# FORGEWORLD PERCEPTION GATEWAY — PROOF 001 Execution Report

## Mission

> Extend the existing ForgeWorld runtime so a screenshot can become a
> provenance-aware observation, a collection of candidate sources, and —
> only after independent verification — a governed knowledge contribution.

Branch: `claude/perception-gateway`. Built on top of
`origin/claude/forgeworld-whatsapp-membrane-sj47yn` merged with
`origin/claude/forgeworld-authority-separation` (see
`perception/governance/00_DISCOVERY_REPORT.md` for the full inspection and
reuse map — that document is the mission's required "Repository inspection
report" and "Reuse map" deliverables and is not repeated here).

## What was built

Twelve stages, each implemented in one focused module under
`perception/src/`, each independently unit-tested before the next was
built (raw smoke-test transcripts are not reproduced here; the committed,
re-runnable equivalent is `perception/tests/`):

| Pipeline stage | Module | Object(s) produced |
|---|---|---|
| CAPTURE, HASH | `ingest.py` | `VisualObservation` |
| OCR | `ocr.py` | `ExtractedSignal` (`signal_type=ocr_text`) |
| VISUAL FINGERPRINT | `ocr.py` (+ `imaging.py`) | `ExtractedSignal` (`signal_type=visual_fingerprint`) |
| ENTITY EXTRACTION | `entities.py` | `ExtractedSignal` (`signal_type=entity`) |
| CANDIDATE RETRIEVAL | `retrieval.py` | `CandidateSource` |
| SOURCE CORROBORATION | `corroboration.py` | `EvidenceRelationship`, `ContradictionRecord` |
| CLAIM EXTRACTION | `claims.py` | `ExtractedClaim` |
| EVIDENCE CLASSIFICATION | `claims.py` (claim's own `validation_status`) | — |
| CAPABILITY PROPOSAL | `proposal.py` | `CapabilityProposal` |
| HUMAN PROMOTION GATE | `promotion.py` | `PromotionDecision` |
| KNOWLEDGE VAULT | `promotion.py` | `perception/ledgers/knowledge_vault.jsonl` entries |

`pipeline.py` sequences all of the above; `cli.py` +
`perception/scripts/forge-perception` is the phone-first command surface
("Mission Control" for this system — see the Discovery Report for why no
dashboard was built).

## A run found and fixed one real bug

While building `entities.py`, a naive substring match (`"x" in text.lower()`)
matched the single-letter platform name **"X"** inside the unrelated word
**"Cortex"** — every screenshot mentioning "Pocket Cortex" would have
spuriously "recognized" the X (Twitter) platform. Fixed by switching to
word-boundary regex matching (`\bX\b`); a standalone "Follow us on X"
still matches correctly. Regression-committed as
`perception/tests/test_ocr_entities.py::test_short_platform_name_does_not_false_positive_inside_unrelated_word`.

A second issue was caught and fixed in the *fixture generator itself* (not
production code): the first version of the synthetic screenshot pattern
used 60px "cards" inside a 64px image, so the perceptual fingerprint's
9-point sampling grid never crossed a card boundary — every fixture,
including the deliberately "different" one, hashed to the same degenerate
all-zero fingerprint. Fixed by aligning the pattern's cell size (8px) with
the fingerprint's 8×8 sampling grid; re-verified that `screenshot_1554.png`
and `screenshot_1555.png` now hash identically (hamming distance 0) while
`screenshot_different.png` diverges (hamming distance 42).

## What was deliberately NOT built

- No live OCR/vision provider wired to a real network call
  (`ocr.CloudOCRProvider`, documented, raises `NotImplementedError`).
- No live web-search/retrieval provider wired
  (`retrieval.WebSearchProvider`, documented, raises `NotImplementedError`).
- No dashboard, no new database, no new queue or background service.
- No change to `whatsapp/` or `governance/` behavior for existing
  capabilities — the only governance change is a new, additive
  `POLICY-promote-knowledge-v1` policy fixture (capability
  `PROMOTE_KNOWLEDGE`, `HUMAN_ONLY`) required for the Human Promotion Gate
  to have anything to check `evaluate_authority()` against.
