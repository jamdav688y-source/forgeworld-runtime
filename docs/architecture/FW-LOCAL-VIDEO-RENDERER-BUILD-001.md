# FW-LOCAL-VIDEO-RENDERER-BUILD-001
## Implementation directive for the first local rendering capability

Status: build directive
Parent architecture: [FW-VIDEO-CAPABILITY-HARVESTER-001](FW-VIDEO-CAPABILITY-HARVESTER-001.md)
Target repository: jamdav688y-source/forgeworld-runtime
Working branch: codex/video-capability-harvester-v0-1

## Mission

Implement ForgeWorld's first useful local video-rendering capability. It must turn an explicitly authored, versioned project graph and user-selected media assets into a preview and downloadable video file on the user's own computer.

The renderer must work without paid generation services, cloud rendering, or credit-consuming APIs. It may use installed local media tools and local compute. Do not describe electricity, storage, dependencies, optional model downloads, or YouTube quotas as cost-free.

Build a bounded rendering capability, not a whole nonlinear editor. Keep its project contract stable so later timeline editing, additional visual effects, local models, source harvesting, and YouTube upload can plug in without rewriting the renderer.

## Repository integration

Create a small `video_creation/` Python package for the local render capability. Keep existing CXP, episode, and production modules authoritative for episode provenance and human production review. Do not change `cognition/production.py` so that production approval grants execution or publication authority.

Add an adapter between the existing production package and video projects. It must accept a `PackageBuilder`-validated package plus an explicit media manifest. It must preserve the package ID, exact candidate revision, scene IDs, citations, and disclosure labels in the resulting project and media receipt.

A production package contains scene instructions and visual prompts, not footage. Never imply that prompts are rendered footage. Every rendered scene must be mapped to a user-selected or licensed asset, or to a clearly declared local graphic generated by the renderer. If any required scene lacks a usable asset, stop with a structured missing-asset report.

Before building from a candidate, re-check that its current production status is `APPROVED_FOR_PRODUCTION` and that the exact candidate revision remains current. Package integrity alone is not current approval. Rendering creates a draft media artifact; it never authorizes publication.

## Package layout

Create the following modules, adapting names only when repository conventions require it:

`video_creation/project.py` defines and validates the project graph and render profile.
`video_creation/assets.py` inspects selected input assets, resolves safe paths, computes SHA-256, and confirms each asset still matches the recorded hash.
`video_creation/ffmpeg_backend.py` detects and invokes the local FFmpeg / ffprobe command-line tools.
`video_creation/plan.py` compiles a project graph into a deterministic, inspectable render plan.
`video_creation/receipt.py` writes a content-addressed render manifest and validation results.
`video_creation/production_adapter.py` connects a validated production package to the media project without changing its approval or publication state.
`video_creation/cli.py` exposes local diagnostics, project validation, preview render, final render, and output inspection.
`video_creation/tests/` contains contract, safety, render-plan, and synthetic-media integration fixtures.

Keep UI integration for a later cycle. The first usable interface may be the repository's existing command pattern, with clear structured output suitable for a future desktop or phone controller.

## Versioned project contract

Define JSON schema version `forgeworld.video.project.v1`. Use strict validation: reject unknown enum values, non-finite numbers, invalid durations, missing references, duplicate IDs, unsupported effects, and ambiguous time units.

Represent time in integer milliseconds at the project boundary. During compilation, convert timeline positions to an explicit rational frame rate and integer frame counts. Never accumulate floating-point frame offsets across scenes.

A project must contain:

`project_id`, schema version, creation and revision identifiers.
A production-package reference, candidate ID and revision when built from an episode.
An explicit output profile: width, height, rational frame rate, pixel aspect ratio, fit mode, video codec, audio codec, and target quality.
An asset inventory with stable IDs, selected absolute paths, hashes, media kind, dimensions, duration where known, and rights or provenance status.
An ordered scene list with stable scene IDs, associated production scene IDs, source asset IDs, source in/out points, timeline duration, fit behavior, approved motion preset, title and caption cues, and audio references.
Optional audio tracks with asset ID, source range, timeline offset, gain, and declared fade settings.
A declared end policy for audio and video so the result never truncates an asset or silently extends beyond the project.
A provenance and disclosure section copied from the validated production package without weakening its labels.

Support user-provided media files and declared generated graphics. Do not fetch remote media automatically. Do not assume that the presence of a file grants rights to publish it.

Initial profiles should include 9:16 vertical and 16:9 landscape, with a preview profile. Use even dimensions compatible with the selected pixel format. Never stretch source imagery to force a fit: support explicit `contain` padding and `cover` cropping. Record crop decisions in the plan and receipt.

## First render feature set

The first release must support a short video with two or more scenes, using combinations of still images and existing video clips.

Support source in/out points, scene ordering, hard cuts, fit-to-frame transforms, a title per scene, timed text or subtitle sidecars, and an optional audio track. Generate a preview at reduced dimensions and a final MP4 at the selected output profile.

Keep effects deliberately small and inspectable. Use only named, versioned motion presets. The first default may be a static shot; optional pan or zoom presets must have fixed, documented bounds and deterministic results. Do not expose raw FFmpeg filter strings to projects or user input.

Compile filter graphs from validated typed fields. Escape filter values correctly, or generate safe intermediate overlay assets. Pass process arguments as an argument list with `shell=False`; never concatenate a shell command from paths, captions, titles, or metadata.

Use hard cuts for v1. Add dissolves, complex compositing, optical flow, stabilization, and generative video only as later capabilities with their own evidence, fixtures, measured cost, and rollbackable versions.

## Local toolchain and dependency handling

Probe `ffmpeg`, `ffprobe`, required filters, encoders, and version before rendering. Fail with a clear diagnostic if a requested feature is absent. Do not silently switch codecs, alter the aspect ratio, or omit audio.

Use the toolchain installed on the user's machine for the initial version. Record binary path, version, build configuration, and selected encoders in the receipt. Before redistributing an FFmpeg binary or building it into an installer, audit the exact configuration and licenses of FFmpeg and its enabled components. The upstream project documents LGPL as its default license and notes that optional GPL components change the applicable license; an FFmpeg binary's actual build configuration matters. Keep this as a release gate, not an assumption.

Upstream references:
https://ffmpeg.org/ffmpeg-filters.html
https://ffmpeg.org/ffprobe-all.html

## Render job behavior

1. Load and strictly validate the project graph.
2. Revalidate the production approval and package lineage when present.
3. Resolve every asset under an allowed user-selected root. Resolve symlinks before checking containment. Reject path traversal and missing files.
4. Hash all assets and compare with pinned hashes. A changed input requires an explicit project revision; never silently update a pinned asset.
5. Probe media and validate source ranges, streams, dimensions, duration, and audio availability.
6. Compile a deterministic render plan and record it before execution.
7. Render to a unique temporary path beside the requested output.
8. Report progress, cancellation, process exit status, and bounded stderr diagnostics.
9. On cancellation or failure, remove only this job's temporary files and preserve the previous valid output.
10. Run ffprobe on the completed temporary output. Verify file readability, expected duration within one frame, output dimensions, frame rate, video stream, expected audio stream, and selected codecs.
11. Compute output SHA-256 and write a receipt. Promote the verified output into its final path using an atomic replace operation.
12. Preserve the project, plan, receipt, and error record. Never overwrite an existing user file without an explicit replace option.

Cache reusable intermediate output only when the cache key includes the canonical project graph, source hashes, renderer version, FFmpeg path/version/build features, profile, and all render parameters. A cache hit must be verified before reuse.

## Safety and resource limits

Use configurable caps for input bytes, project duration, scene count, output dimensions, process runtime, concurrent render jobs, and temporary storage. Defaults must be conservative and documented.

Do not accept arbitrary executable paths from a project file. Do not invoke a shell. Do not write outside the project output and temporary directories. Do not delete source assets. Keep credentials entirely out of the local render module.

On unsupported or malformed input, fail closed and return a structured error code, explanation, affected scene or asset ID, and next action. Never return a successful status when ffprobe validation failed.

## Render receipt

Write a JSON receipt with schema version, media artifact ID, project ID and revision, package ID and candidate revision, creation time, toolchain information, render profile, render-plan hash, input asset IDs and hashes, output path and SHA-256, output probe summary, runtime measurements, cache result, validation checks, warnings, and failure details when applicable.

The receipt must state:
`publication_authorized: false`
`upload_status: NOT_ATTEMPTED`
`evidence_status: GENERATED_MEDIA_NOT_SOURCE_EVIDENCE`

The receipt identifies how an artifact was generated; it does not certify the truth of claims shown in the video or grant the right to publish its assets.

## Required validation work

Implement synthetic fixtures that do not rely on copyrighted footage or network services. Generate test color frames, short tone audio, and known-good media with FFmpeg at runtime when available.

Cover valid still-only and mixed still/video projects, portrait and landscape profiles, timed titles or subtitle sidecars, optional audio, and preview-to-final settings.

Cover missing and changed assets, path traversal, symlink escape, duplicate IDs, invalid source ranges, unsupported profiles, unavailable tools or filters, malformed project JSON, process timeout, cancellation, partial output cleanup, and failed ffprobe validation.

For successful renders, compare the result to explicit invariants rather than brittle whole-file byte identity: dimensions, frame rate, duration tolerance, stream presence, monotonic scene order, expected text timing, audio bounds, readability, and stable project/plan hashes.

Run the focused renderer checks, then the existing cognition and repository regression suites. Report commands, pass/fail counts, skips, environment, and any untested platform. Do not claim cross-platform behavior based on one operating system.

## Acceptance criteria for v1

A user can create and validate a project using local assets only.
The renderer can produce a short downloadable MP4 containing at least two scenes, titles or timed text, and optional audio.
Both vertical and landscape profiles render with correct aspect handling and no stretched media.
A preview and a final render use the same scene plan, with differences limited to declared quality and dimension settings.
The output is inspected by ffprobe and accompanied by a receipt that preserves asset hashes and production-package lineage.
A missing or changed asset, invalid approval, unavailable codec, failed render, or invalid output cannot be reported as successful.
The render works without paid generation services and without network access after the local toolchain and inputs are present.
No upload or publication is attempted.

## Implementation sequence

Cycle 1: inspect repository packaging, Python version expectations, test conventions, existing command entry points, and production package loading. Record findings before editing.
Cycle 2: add the project schema and strict validator, then asset resolution and hashing.
Cycle 3: add FFmpeg capability discovery and render-plan compilation.
Cycle 4: implement preview and final rendering with safety bounds and atomic output handling.
Cycle 5: add receipts, production-package adaptation, and the CLI.
Cycle 6: implement synthetic fixtures, run focused and regression checks, and fix all observed failures.
Cycle 7: demonstrate one locally rendered vertical video from licensed synthetic or user-selected assets. Preserve the exact project, plan, receipt, and command output as the first verified capability record.

After each cycle, send measured telemetry to ForgeWorld's event/history path and update the capability gap report. Do not promote the renderer until its acceptance criteria and regression checks pass.
